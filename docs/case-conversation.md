# Unified Case Conversation

The Case list Date is the server-recorded creation time (`createdAt`), not the
reported incident start time (`occurredAt`). It remains unchanged by later chat.

The Case composer uses `POST /api/incidents/:id/messages` for both new and
previously analyzed incidents, including questions with selected attachments.
The legacy report-chat and document-question endpoints remain compatible.

## Per-Turn Flow

1. Persist the user message with its request ID and selected document IDs.
2. Call the existing Case Intake Agent to extract facts from user statements.
   Preserve evidence checks, explicit unknowns and conflict confirmation.
3. Match the updated facts against active, approved runtime Pills using existing
   category, asset-prefix and keyword applicability rules. Demo and draft Pills
   are excluded. Supply up to eight matched Pills to the answer model.
4. Call the Case Conversation Agent with current facts, recent conversation,
   missing information, safety uncertainty, matched knowledge and selected file
   excerpts. This is a separate model request after extraction, not a fixed
   template or a single streaming call. No matching Pill is a knowledge gap, not
   permission to invent an operational procedure.
5. Validate cited source IDs and verbatim quotes. Save citations with Pill
   versions or document locations. Reject replies if selected Pill releases
   changed during inference. Persist the answer and extracted facts together
   using the existing case revision check.

The reply is generated by the LLM. The original template function remains for
legacy injected extraction-only adapters; the production conversation path
does not silently replace model failures with template replies.

## Conversation and Governance

- The assistant answers the question and may ask one contextual follow-up.
  Validated follow-up identifiers preserve the meaning of short answers even
  when the question is rephrased or translated.
- Attachments are reference material, not automatically confirmed facts or
  approved Pills. Only user statements enter the existing fact extractor.
- History from a previous report is marked historical, not current approval.
- The Case page has one chat and two follow-up panels: Expert experience confirmation and
  Summary. Summary displays only one paragraph; structured feedback and evidence
  remain stored for governance, not displayed as separate Case fields.
  Report-generation and manual outcome forms are no longer
  shown on this page. Legacy report APIs and saved records remain intact.
- Expert experience confirmation displays submitted solutions, authors and
  timestamps. After submission the input form and duplicate chat receipt disappear.
  An expert/admin can confirm and save an experience as a Pill draft using
  POST /api/cases/:id/expert-experience-confirmation. Requests are revision-checked
  and import is idempotent. The original author and confirming person are distinct
  audit fields. Operational review/escalation remains in the conversation; old
  confirmation records remain stored. Knowledge confirmation is not execution
  approval. Decorative knowledge-gap/advisory footers and message dividers are
  removed, but backend policy and source citations remain intact.
- The answer model automatically returns an evidence-linked result/feedback
  summary each turn. Existing Cases without a current summary are summarized
  when an authorized user opens Summary. A reported outcome is never
  marked independently verified by the model or used to close a Case.
- When the model identifies a solution requiring expert judgment, an inline
  text box collects the expert solution. Draft applicability defaults to this
  Case only; broader scope and safety limits require validation. Only expert
  or administrator accounts can submit it. Server-controlled identity is saved.
- Expert submissions first remain in the Case as pending_confirmation. Only the
  subsequent confirmation enters a new or existing Pill draft as captured knowledge.
  Published versions are untouched. Existing incorporation, validation and
  independent publication review gates remain required. Saving a source does
  not automatically convert it into validated executable rules.
- JSON mode stages the expert solution before idempotent draft import, so a
  failed import can be retried; SQLite wraps Case and Pill writes in a transaction.
- Chat updates return the case to draft/information collection. Legacy formal
  reports still require case confirmation; new messages invalidate snapshots.
- The AI cannot approve actions, execute equipment commands, or publish Pills.
  Authorized reviewers can record a recommendation-specific decision in chat;
  this is not an execution permit, an automated dispatch, or a Pill release.
- Failed requests keep the user message for retry. Retrying retains document
  selection and does not duplicate successful turns. Unauthorized document IDs
  are rejected before model invocation.

## Boundaries and Verification

Post-Case learning belongs to Pill Studio / Improvement queue. Its Case selector
loads conversation evidence, human decisions, expert draft links and the existing
action/outcome verification and learning controls. Proposals are reviewed there,
then incorporated, validated and released through the Pill draft workflow.
Learning snapshots include user reports, human decisions, expert proposals and
the AI summary with explicit unverified/not-executed labels. Conversation evidence
can start an analysis, but does not satisfy verified action/outcome requirements
for knowledge-change proposals. For conversation-only Cases, the target is a
referenced approved Pill at the same version; stale references require a fresh
assessment. No Case summary automatically changes a published Pill.

### Case Supervision

The model classifies knowledge gaps, scope uncertainty, conflicting evidence,
specific approval requirements, safety escalation and explicit expert requests.
Routine questions and missing facts should remain ordinary conversation. The
server independently requires review for cited Pill actions carrying an approval
flag, while unresolved scope/conflicts require expert judgment first. A model
approval request without a cited approval-bearing action is downgraded to expert
scope review, not an approvable operational recommendation.

Independent bilingual operation checks cover equipment restart/reset/shutdown,
parameter changes, energy isolation/restoration, intrusive maintenance and
critical-service interventions. Without validated approval-bearing action
coverage these requests require expert input, even if the model says no review
is needed. Protection/alarm bypass or disable requests escalate instead of
offering ordinary approval. The user does not need to mention a missing Pill or
ask for an expert. Basic definitions, negations and past reports are excluded
from these pattern checks. Direct model-generated operation advice is checked
too and replaced with a review/assessment notice when detected.

These are conservative MVP rules, not an exhaustive semantic classifier or
engineering safety certification. Paraphrases and complex negation can still
be missed or over-triggered. A matching action category only opens human review;
the reviewer must check actual suitability and local authority.

Expert requests use the existing expert-solution-to-draft path. Review requests
allow approved, rejected or escalated decisions from reviewer/admin accounts.
Safety requests allow only an escalation record, never approval. An escalation
record documents a human-reported handoff; no external notification is sent.
The server binds decisions to the stored message, subject, Pill versions and
authenticated identity. It rejects duplicate decisions, stale revisions, and
approval after referenced releases or extracted Case facts change. Changes in
unextracted discussion still require reviewer judgment. Rejection and escalation
remain possible for obsolete recommendations.

Outstanding requests and prior decisions are included in subsequent model
context. Conversation can continue while a request is pending; the application
has no equipment-execution capability. Approval applies only to the recorded
recommendation, never future chat or published knowledge. Model-based request
deduplication is advisory, not a guaranteed semantic equivalence check.

The reply model uses the existing SOCLAAS environment configuration and model
transport. No new key is required. Restart the backend after deploying.

Automated tests cover contextual model requests, extraction, Pill scope/status,
citations, release revocation, short-answer tracking, persistence, retries,
attachment ownership and the unified frontend endpoint. Model requests are
mocked in these tests. Exact citation validation checks provenance, not the
clinical or engineering correctness of free-form explanations; prompt guardrails
and automated tests are not expert safety certification.
